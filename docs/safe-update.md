# آپدیت امن یک‌مرحله‌ای

روی میزبان Linux، داخل checkout موجود و با دسترسی Docker:

```bash
bash update.sh
# نسخهٔ دقیق بازبینی‌شده (SHA کامل main):
bash update.sh --target FULL_40_CHARACTER_MAIN_SHA
# فرمان مدیریتی نصب‌شده نیز همین مسیر را صدا می‌زند:
usermanager update
# یا:
bash install.sh update --dir /opt/usermanager
```

پیش‌نیاز: شاخهٔ main، فایل‌های tracked بدون تغییر، بک‌اند سالم، Python 3 و
flock و coreutils timeout روی میزبان و فضای کافی برای ساخت دو image و دو نسخهٔ بکاپ. هیچ فایل
env یا دادهٔ untracked حذف نمی‌شود. این مسیر نصب اولیه نیست.

آپدیتر و helper همراهش نخست باید با استقرار بازبینی‌شده روی نصب قدیمی قرار
بگیرند؛ اسکریپت قدیمی خودکار قابلیت‌های جدید را ندارد. از آپدیت‌های بعد همین
دستور کافی است. fetch پس از ۹۰ ثانیه متوقف می‌شود و URL/credential چاپ
نمی‌شود. سلامت frontend با انتظار محدود بررسی می‌شود. اگر دیتابیس بات از
مسیر تنظیم‌شده پیدا نشود، آپدیت متوقف می‌شود؛ نبود آن را به‌جای بکاپ خالی
تلقی نکنید و تنظیم مسیر/غیرفعال‌بودن بات را جداگانه بررسی کنید.

مسیر update در نصاب قبل از تغییر env، فایل state، دریافت سورس یا بازسازی
سرویس‌ها به آپدیتر امن تحویل می‌شود. update همراه `--port`، `--source`،
`--repo` یا گزینهٔ ناشناخته رد می‌شود؛ تغییر تنظیمات را جدا انجام دهید.
نصب اولیه تغییر نکرده است.

**دکمهٔ «بروزرسانی پنل»** همین update.sh را اجرا می‌کند، نه مسیر جداگانه:
- فقط superadmin، با رمز خودش، تأیید دوم و SHA کامل main که «بررسی» نشان داده است.
- API هیچ pull، reset، کنارگذاشتن تغییرات سرور، build یا restart انجام نمی‌دهد. فقط یک job در `backend/data/update-runs` ثبت می‌کند.
- job در یک کانتینر خواهر با image ID ثابت backend فعلی اجرا می‌شود و از جایگزینی backend جان سالم به در می‌برد. قفل آن همان قفل update.sh در CLI است.
- همهٔ فایل‌های منجمد (runner، update.sh، helper، compose، shimهای docker و flock) با digest بررسی می‌شوند. digestها در Cmd تغییرناپذیر کانتینر لنگر شده‌اند. سپس فایل‌ها در فایل‌سیستم خود کانتینر کپی و دوباره بررسی می‌شوند و update.sh از همان کپی اجرا می‌شود.
- کل اجرا مهلت ۶۰ دقیقه دارد. در پایان مهلت یا با SIGTERM، کل گروه فرایند update.sh متوقف می‌شود (TERM و سپس KILL).
- رمز یا token در فایل‌های job، لاگ یا آرگومان فرایند نیست. خروجی خام git/build ذخیره نمی‌شود؛ فقط مرحله‌ها ثبت می‌شوند.
- بکاپ میزبانِ این مسیر زیر `backend/data/update-runs/<job>/backup` است.

وضعیت job روی دیسک می‌ماند و UI پس از restart، قطع شبکه یا تازه‌کردن صفحه آن را ادامه می‌دهد. دوبار کلیک یک job می‌سازد. «موفق» فقط وقتی اعلام می‌شود که خود worker پایان کامل update.sh (UPDATE_OK برای همان SHA و خروج صفر) را ثبت کرده باشد. پاسخ‌دادن backend به‌تنهایی موفقیت نیست.

وضعیت نامعلوم مانع آپدیت تازه است:
- مهلت تمام‌شده، worker ازبین‌رفته وسط اجرا، Docker در دسترس نبودن یا شروع مبهم.
- کانتینری که ساخته شده ولی شروع نشده (created) شکست نیست. خطای مبهم create/start هم «هیچ کاری نشد» نیست.
- اپراتور پس از بررسی سرور می‌تواند job را با رمز و تأیید ببندد. کانتینر شروع‌نشده حذف می‌شود؛ اجرای قطع‌شده فقط وقتی «abandoned» ثبت می‌شود که قفل update.sh آزاد باشد.
- هیچ rollback یا بازگردانی دیتابیس انجام نمی‌شود.

پیش از بکاپ و checkout، imageهای پایهٔ Dockerfileهای commit هدف (دقیقاً همان
ارجاع‌های FROM، با همان pin) بررسی می‌شوند. imageی که روی سرور هست به شبکه
نیاز ندارد؛ نبودِ آن با حداکثر سه بار pull (فاصلهٔ ۳۰ و ۶۰ ثانیه، هر بار حداکثر
۱۰ دقیقه) جبران می‌شود. اگر registry در دسترس نباشد، آپدیتر پیش از هر تغییری با
STOP متوقف می‌شود (بدون بکاپ، checkout یا build) و باید بعداً دوباره اجرا شود.
build همچنان ممکن است به‌دلیل دیگری شکست بخورد؛ در آن صورت هیچ سرویسی
جایگزین نمی‌شود ولی checkout روی SHA هدف می‌ماند.

قبل از تغییر checkout، پنل از DATABASE_URL و بات از BOT_DB_PATH (با پیش‌فرض
رسمی خودش) بکاپ مستقل می‌گیرند. SQLite با online backup و integrity_check
روی کانتینر و میزبان بررسی می‌شود. MySQL/MariaDB از dump موجود با
single-transaction استفاده می‌کند؛ جدول غیر InnoDB رد می‌شود. خروج موفق dump،
غیرخالی‌بودن و SHA بررسی می‌شود؛ این معادل آزمون واقعی restore نیست. این دو
بکاپ جدا هستند، نه snapshot اتمی بین پنل و بات. هیچ پیام تلگرامی ارسال نمی‌شود.

بکاپ میزبان زیر `/var/backups/usermanager/update_*` مستقل از mount کانتینر
می‌ماند؛ مسیر را می‌توان با UM_UPDATE_BACKUP_DIR (absolute و خصوصی) تعیین کرد.
فایل‌ها 600 و پوشهٔ هر اجرا 700 است. بکاپ کانتینر نیز زیر BACKUP_DIR می‌ماند.
هیچ‌کدام خودکار پاک نمی‌شوند؛ مدیریت فضا و نگهداری بر عهدهٔ اپراتور است.

فقط fast-forward به main انجام می‌شود. هر دو image قبل از توقف ساخته می‌شوند؛
image و SHA قبلی برای بازگشت کد ثبت می‌شوند. فقط backend و frontend با
`--no-deps` بالا می‌آیند؛ license-server و MariaDB ری‌استارت نمی‌شوند.
modeهای P6، مالکیت، typeها، کیف‌پول، تأیید رسید، Void و سقف نشست پیش و پس از
استقرار مقایسه می‌شوند. این اسکریپت هیچ activation، claim، reclaim، probe،
تأیید تصمیم محصول، یا تغییر مالی انجام نمی‌دهد. اگر جدول قدیمی نبوده و پس از
update ظاهر شود، مقایسه STOP می‌دهد و اپراتور باید تغییر را بررسی کند.

عملیات durable باز، تغییر تنظیمات حین build، یا خطای backup/build/health
باعث STOP می‌شود. بررسی readiness یک drain اتمی نیست؛ در ساعت کم‌ترافیک
اجرا کنید، چون درخواست تازه ممکن است بعد از check آغاز شود. خطا پس از
شروع استقرار می‌تواند بک‌اند جدید و فرانت‌اند قبلی را باقی بگذارد؛ موفقیت
کلی اعلام نمی‌شود. لاگ خام یا credential در خروجی آپدیتر چاپ نمی‌شود.

در خطا mode را خاموش یا DB را از بکاپ جایگزین نکنید. سازگاری schema و علت
خطا باید بررسی شود، سپس با SHA و imageهای ثبت‌شده تصمیم بازگشت کد بگیرید.
هیچ rollback خودکار یا DB restore وجود ندارد. بعد از reboot میزبان P6 ممکن
است reclaim احراز هویت‌شده بخواهد؛ این محافظت دور زده نمی‌شود.
